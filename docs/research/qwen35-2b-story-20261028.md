# Qwen3.5-2B short-window video storyline probe — 2026-10-28

## Question

Can Qwen3.5-2B produce useful, ordered descriptions of real video in under 3 seconds, either as one 50-second summary or as short observations that a brain can join into a story?

## Setup

- Model: [Qwen/Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B), pinned revision `15852e8c16360a2fea060d615a32b45270f8a8fc`, BF16 safetensors; 4,548,221,488 bytes, SHA-256 `aa33250c4fc64891ddfaba3a314fd9542ea371843c387178b425fbcc5ed680b1`.
- Runtime: Transformers 5.20.2, PyTorch 2.14.1+cu130, RTX 5080 GPU1. Non-thinking mode; warm-up used a separate excerpt. No application profile or project dependencies changed.
- Source: the fixed 50-second montage with five 10-second sections: Russian trailer, anime, RTS gameplay, coding UI, Aqua performance. Video-only. Reference: `runtime/multimodal-realclips-20261024/visual-ground-truth-1fps-20261024.json`.
- Frames: 1 fps. One 10-second window therefore has 10 frames; the whole montage has 50. The processor's preparation time and model inference time are reported separately.
- Grounding rule: reference ledger records visible facts and explicitly leaves ambiguous trailer/anime details unresolved. A plausible guess is not scored as verified.

## Results

### One whole-montage request

The model received all 50 sampled frames, 11,891 prompt tokens, and a 128-token answer cap. Warm inference p50 was **5.16 seconds**; preprocessing was **0.51 seconds**, for **5.67 seconds end to end**. All three answers hit the cap after the first part of the gameplay scene. They preserve the opening-to-anime-to-game order but do not reach the coding or performance sections. This mode misses the 3-second target and does not return a complete story.

### Separate 10-second windows

Each window got its own prompt. Order between windows is preserved by the capture timestamps, not inferred from a single request.

| Window | Concise BF16 prompt, 48-token cap | Result | Grounding against the reference |
|---|---:|---|---|
| Trailer | 1.33 s end to end | Two people outdoors, then a dark profile/man | The visible close contact is real, but “embrace” over-interprets a shoulder-support pose. Smoking is explicitly unresolved in the reference, yet asserted. |
| Anime | 1.67 s | Anime character, title card, students; other prompts gave lab coat/chained person | Some broad sequence recognition, but specific actors/actions are unsupported; an alternate “literal” prompt still invented a chained body and gun. |
| RTS | 1.50 s | Units, plant, explosions/damage numbers | Strong match to visible battle, HUD, and the distinctive carnivorous plant. |
| Coding UI | 1.28 s | Model list and cursor | Correct broad interface and cursor movement. Fine text claims vary and are not all verified by the ledger. |
| Music video | 1.48 s | Performer, keyboard, couch, bubbles | Strong match to visible performer, microphone, seated man, keyboard shot, and bubbles; it cannot establish what is heard. |

All five concise outputs were repeat-stable. The useful details are materially better than Florence's generic captions, but the trailer and anime windows contain confident unsupported claims. Strictly asking for a literal visual log did not fix those errors.

With a less restrictive multi-event prompt, output quality was inconsistent with the latency ceiling: RTS and coding windows completed in about **2.4–2.5 seconds**, but anime and music windows took about **4.0 seconds** and still hit the token cap. A single whole-montage request remains over the limit.

### One-image storyboard variants

To reduce the long-video prefill, five representative frames (one per section) were laid out in chronological order as a labeled image. Three deterministic runs took **1.47 seconds end to end** (1,691 input tokens). The answer identified a progression through a dark scene, red logo, combat game, interface, and close-up, but called two people “women,” misread the coding UI as chat, and missed that the last image belonged to a performance/music video. It is fast enough only because it collapses each 10-second section to one still.

A denser storyboard used three frames from each section (15 frames, 2,730 input tokens) and requested one line per section. Its p50 was **3.80 seconds**; all three runs hit the 128-token cap and stopped partway through section four. More within-section detail pushed it outside the latency target without preventing the earlier unsupported claims.

### Q4_K_M llama.cpp check

Also tested `gguf/Qwen3.5-2B-GGUF:Q4_K_M` (1,312,164,352-byte model; F16 mmproj 668,226,656 bytes) on GPU1 with llama.cpp 0.8.0-dev build 290, prompt caching off, non-thinking, and five 640-pixel frames per window. With the standard image token budget, warm HTTP latency was **0.29–0.44 seconds** for 5 frames and 29–80 generated tokens. The quant is much smaller, but it did not remove content errors: it repeatedly called the ambiguous trailer point a cigarette, hallucinated bubbles in the anime, inferred a plant eating an object, and cut off some detailed captions at a 48-token cap; at 96 tokens they stopped normally but remained unsupported in places. It is a speed/size option, not a quality winner.

An additional high-resolution Q4 attempt set 1,024 image tokens per frame. The first window took about **0.84 seconds**, but subsequent image batches failed in this llama.cpp build with `failed to prepare attention ubatches` / `failed to decode mtmd chunk`. No high-resolution Q4 score is claimed. The test server was stopped after these runs; application profiles were not touched.

## Decision

**Best current candidate for fast visual observations: Qwen3.5-2B BF16, one concise caption per 10-second window.** It provides more scene detail than Florence and better per-window context than the smaller Qwen3.5-0.8B trial, while typical compact captions stay around 1.3–1.7 seconds on GPU1. The Q4 version is substantially smaller and faster but does not improve accuracy.

This is a provisional selection, not a pass for reliable plot narration. The anime and trailer errors mean the observations need uncertainty handling or corroboration; the whole 50-second direct-summary prompt misses the latency target. The test also does not prove a complete Qwen3.5-to-Hikari story pipeline or live capture throughput. For reference, the earlier [Qwen3.5-0.8B trial](qwen08b-story-cpu-gpu-20261028.md) was much faster on 8 frames but also hallucinated scene details; [Florence tags to brain](florence-tags-to-brain-20261028.md) did not reconstruct a dependable plot; [LFM3-Omni](lfm3-omni-story-20261028.md) and [Marlin-2B](marlin-2b-story-20261028.md) did not meet the combined target either.
