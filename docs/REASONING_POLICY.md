# Reasoning и режимы компаньона

## Основное правило

Быстрый разговор и выполнение цели — разные режимы. В обычном диалоге
провайдеру передаётся минимальный доступный reasoning (`none`, если модель
его поддерживает). Ответ должен быть коротким и пригодным для немедленной
озвучки.

Явная команда пользователя вроде «поставь задачу», «создай goal», «сделай
план и выполни» переводит текущий turn в `goal_execution`. Это не должно
срабатывать на случайное слово «цель» в обычной фразе: intent должен быть
подтверждён структурированным JSON-намерением и описанием результата.

## Goal execution

JAWL остаётся владельцем цели, checkpoint, памяти, native tools и heartbeat.
Внутри goal разрешается повышенный reasoning (`low`/`medium`/`high` по
политике конкретного провайдера), но только для планирования и проверяемых
шагов. Для простых tool-call шагов reasoning снова снижается. Модель с
принудительным thinking не ломается искусственным `none`: адаптер принимает
её ограничение, но сохраняет отдельные бюджеты и таймауты.

Каждый шаг обязан иметь correlation id, статус, checkpoint и postcondition.
Повтор шага допускается только если он идемпотентен или имеет deduplication
key. Подробный ход выполнения хранится в журнале и доступен в чате по запросу.

## Голосовой слой

Озвучиваются только:

- подтверждение принятия цели;
- короткие checkpoints («проверяю файлы», «шаг завершён»);
- блокер, требующий решения пользователя;
- итог.

Внутренние reasoning-токены, ReAct-трасса и длинные отчёты не попадают в TTS.
Пользователь может запросить подробности в чате или голосом. Один active
speech owner и bounded playback buffer сохраняют возможность barge-in.

## Приёмка

Нужно доказать минимум три связанных сценария: быстрый обычный ответ без
лишней задержки; явный goal с двумя checkpoint и восстановлением после
restart; прерывание голосом с отменой TTS без потери checkpoint и дубля
side-effect. Провайдерные capability и фактическое поведение должны быть
записаны в runtime evidence, а не приниматься по одному isolated probe.
