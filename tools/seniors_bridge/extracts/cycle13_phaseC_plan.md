=== ПЛАН ===

Cycle 13 — JAWL LIVE VOICE: Stream-First Duplex и управляемый голосовой арбитраж

Соответствие цели: AC-03 — устранить задержку голосового ответа 11,4–32,7 с, обеспечить быстрое начало речи и barge-in ≤300 мс; AC-01 — создать ощущение непрерывного живого присутствия; AC-05 — обеспечить уместные, ненавязчивые реакции; AC-08 — сохранить производительность и устойчивость GPU 1; AC-09 — гарантировать немедленное подчинение mute/pause.

Приоритет владельца: естественный полнодуплексный голосовой слой уровня MOSS Live.

Единственный видимый результат цикла: JAWL начинает отвечать потоково, не ожидая генерации полного ответа, корректно передаёт управление между Fast Lane и Deliberative Lane и прекращает воспроизведение при перебивании.

Целевые показатели:

Первый слышимый звук / рефлекс: p95 ≤1,2 с.

Завершение короткого содержательного ответа: p95 ≤4,0 с.

Остановка слышимого TTS после обнаружения barge-in: p95 ≤300 мс.

Коллизии воспроизведения, устаревшие ответы, самопроизвольные повторения: 0 в контрольном наборе.

Все задержки измеряются, а не декларируются. Быстрое «Угу» не считается быстрым содержательным ответом.

Не реализовывать семь независимых механизмов одновременно.

3. Пошаговые инженерные изменения
Шаг 1. TurnTrace: установить настоящую причину Voice Latency Floor

AC-03, AC-08. H1 / P0.

В duplex_cascade.py добавить для каждого речевого хода:

turn_id

generation_epoch

t_user_speech_end

t_vad_endpoint

t_asr_final

t_llm_request

t_llm_first_token

t_llm_first_sentence

t_tts_request

t_tts_first_pcm

t_audio_enqueued

t_audio_playback_start

t_audio_playback_end

t_barge_in_detected

t_audio_stopped

Серверные интервалы считать через time.monotonic_ns(), клиентские — через performance.now().

Запрещено напрямую вычитать timestamp разных процессов или устройств. Для сквозного времени использовать корреляцию clock domains с оценкой погрешности либо измерять клиентский интервал от окончания пользовательской речи до фактического playback. Физический первый звук проверять через разрешённый loopback/акустический тест.

Перед изменением алгоритма провести baseline не менее чем на 30 репрезентативных ходах.

Вывести p50/p95 по стадиям:

VAD → ASR → Bonsai first token → Bonsai first phrase → OmniVoice first PCM → playback

Критерий: каждая задержка 11,4–32,7 с раскладывается на измеренные стадии. Неизмеренные интервалы обозначаются UNKNOWN.

Если 80% задержки создаёт один блокирующий await, сначала исправить его. Не пытаться компенсировать дефект префейсами.

Шаг 2. Stream-First: устранить сериализацию полного ответа

AC-03. H1 / P0.

В duplex_cascade.py заменить последовательность:

ASR final → весь Bonsai answer → весь OmniVoice WAV → HTTP response → playback

на:

ASR final → Bonsai streaming → первая завершённая смысловая фраза → OmniVoice streaming → первый PCM → playback

Параллельно продолжать генерацию следующих фраз.

Обязательные требования:

Первая фраза передаётся TTS сразу после появления корректной границы смыслового сегмента.

OmniVoice не ждёт полного текста ответа.

Клиент не ждёт окончания синтеза WAV.

Сегментатор учитывает сокращения, числа, незавершённые слова и пунктуацию.

Ограничить количество PCM-chunks в очереди: недопустимо заранее буферизовать много секунд устаревающей речи.

Если Bonsai не умеет реальную потоковую выдачу через текущий backend, зафиксировать блокер и использовать минимально доступный streaming API без смены модели.

Не отправлять каждое слово в OmniVoice отдельно. Это может ухудшить просодию и вызвать дополнительные расходы на синтез.

Рекомендуемый первоначальный вариант — короткие законченные смысловые фразы, с последующей настройкой размера чанков по измерениям.

Шаг 3. Single-Owner Vocal Tract FSM

AC-03, AC-08, AC-09. H4 / P0.

Разграничить ответственность:

duplex_cascade.py — источник истины для состояния речевого хода, epoch и разрешений на воспроизведение.

desktop/app.js — единственный физический владелец аудиовывода и окончательная защита от воспроизведения устаревшего chunk.

web.py — транспорт, не самостоятельный речевой арбитр.

Минимальные состояния:

IDLE → USER_SPEAKING → RESPONSE_READY → PLAYING → IDLE

Дополнительные переходы: PREFACE_PLAYING, CANCELLED, MUTED.

Инварианты:

Только один поток управляет устройством воспроизведения.

Каждый audio chunk содержит turn_id, generation_epoch, sequence_number.

Chunk принимается только для актуальной эпохи.

Новый подтверждённый пользовательский ход инвалидирует старую эпоху.

Повторный ASR final не создаёт второй ответ.

Отменённый TTS не может возобновить playback после позднего завершения GPU-задачи.

При mute/pause очередь немедленно очищается.

Важная поправка к H4: не увеличивать epoch на каждом сыром VAD-импульсе или промежуточном слове ASR. Это вызовет бесконечные отмены. Epoch изменяется при подтверждённом новом ходе, реальном barge-in или явном пользовательском cancel.

Шаг 4. Гарантированный контроль barge-in

AC-03, AC-09. H5 / P0.

В desktop/app.js:

При подтверждённом barge-in немедленно приглушать активный выход Web Audio.

Останавливать дальнейшее планирование PCM.

Очищать локальную очередь.

Инвалидировать текущий playback epoch.

Отправлять backend сигнал отмены.

На backend:

Инвалидировать соответствующий turn.

Прекратить передачу новых chunks.

Запросить отмену Bonsai/OmniVoice.

Игнорировать результат завершившейся позже CUDA-задачи.

Не ставить успешную отмену CUDA условием остановки звука. Звук должен прекращаться независимо от времени освобождения GPU.

Echo Guard:

Передавать reference PCM собственного TTS в механизм подавления эха, если существующий аудиотракт поддерживает это.

Не считать любое совпадение микрофонного сигнала с TTS доказательством отсутствия владельца.

Проверять реальные случаи, когда пользователь говорит поверх JAWL.

gainNode.gain.setValueAtTime(0) уменьшает уровень воспроизведения, но не доказывает акустическое прекращение за 50 мс: существуют буферы устройства и задержки ОС.

Критерий: p95 ≤300 мс до фактической остановки слышимого TTS на разрешённом loopback/акустическом стенде. Если измерено только программное mute, статус SOFTWARE_BARGE_IN_VERIFIED, не ACOUSTIC_BARGE_IN_VERIFIED.

Шаг 5. Fast Lane: ограниченная рефлекторная дуга

AC-01, AC-03, AC-05. H2 / P1.

Реализовывать только после успешного Stream-First и Single-Owner FSM.

Первоначально использовать небольшой RAM-кэш заранее синтезированных коротких аудиофрагментов OmniVoice в штатном голосе JAWL. В runtime Fast Lane не обращается к GPU.

В web.py допускается /api/voice/preface, но endpoint обязан проверять актуальные turn_id, epoch и разрешение арбитра. Endpoint не должен становиться независимым TTS-плеером.

Fast Lane по умолчанию выключен feature flag.

Условия воспроизведения:

Есть подтверждённая безопасная возможность вставить реакцию, не перебивая пользователя.

Нет активного mute/pause.

Не сработал cooldown.

Префейс не дублирует уже готовый осмысленный ответ.

Реплика не утверждает, что команда выполнена, факт проверен или смысл полностью понятен.

Сначала допускать только нейтральные короткие вокализации.

Фразы вроде «Смотрю» разрешать исключительно при реальном запуске проверки. «Понял» не использовать автоматически по двум словам ASR partial.

Переход Fast → Deliberative:

Если содержательный chunk уже готов — отменить ещё не начатый префейс.

Если префейс звучит — по возможности закончить короткую вокализацию на естественной границе и перейти к смысловому ответу.

Crossfade 50 мс использовать только когда он не разрезает слово и не создаёт наложения смысловых фраз.

При barge-in crossfade не ждать: пользовательский cancel имеет абсолютный приоритет.

Не требовать абсолютной бесшовности при аварийном прерывании. Безопасность и управляемость важнее красоты перехода.

Шаг 6. Антиспам и дедупликация

AC-05, AC-03. H3 / P1.

В affective_engine.py либо в существующем модуле политики TurnArbiter реализовать минимальный admission gate:

Не более одного префейса на пользовательский turn.

Начальный cooldown 6 секунд; значение конфигурируемое.

Token-bucket с ограничением частоты коротких реакций.

Семантическая дедупликация одинаковой функции: «Ага», «Да», «Понял».

Подавление префейса при активной речи пользователя.

Подавление при слишком коротком интервале после предыдущей реплики JAWL.

Полный запрет реакций при пользовательском mute.

Не добавлять отдельную модель определения эмоций или просодическую нейросеть в этом цикле.

Если текущие признаки просодии доступны — использовать их. Если нет — ограничиться VAD/ASR и детерминированными правилами.

Шаг 7. GPU 1 и память: защитить существующий стек

AC-03, AC-06, AC-08. H6/H7 — только инварианты.

Для GPU 1:

Измерить конфликт Bonsai, OmniVoice и Qwen.

Не запускать дополнительные экземпляры моделей ради Fast Lane.

Не останавливать Bonsai ради TTS без доказательства, что это уменьшает end-to-end latency.

Сохранить существующие лимиты VRAM.

Не вмешиваться в Bonsai и сторонние процессы.

Для памяти:

Префейсы не записывать как содержательные ответы.

Отменённые и неозвученные фрагменты не записывать как состоявшийся диалог.

Существующие memory writers проверить на этот инвариант.

Полноценную H7 Shadow-Commit Memory не внедрять сейчас. Если обнаружится ложная запись неозвученного ответа, устранить конкретный дефект минимально.

Важное ограничение измерений

Нужно различать три показателя:

Первый любой звук — может быть префейсом.

Первый осмысленный ответ — действительно полезная информация.

Конец озвучивания ответа — зависит от количества слов и скорости речи.

Для длинных ответов требование «полностью произнести всё за 4 секунды» не является универсально достижимым. Фиксировать длину короткого ответа, длительность аудио и отдельно время завершения генерации.

Если получено 0,5 с на префейс, но содержательный ответ начинается через 12 с, Cycle 13 считается FAILED по основной цели.

Обязательные условия отката

Отключить Fast Lane или вернуть предыдущую реализацию, если обнаружены:

Регулярные перебивания пользователя.

Акустическое самовозбуждение ASR/TTS.

Дублирование реплик.

Увеличение времени первого содержательного ответа.

Стабильная деградация GPU/FPS сверх AC-08.

Невозможность немедленного mute.

Рост длительности Deliberative Lane из-за дополнительного арбитража.

Feature flag должен позволять выключить префейсы без отключения Stream-First.
