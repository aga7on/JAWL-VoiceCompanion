 Ответ A 1. H1 (P0): 60-минутный сенсорный soak существующего контура — единственный основной результат цикла Суть: Заморозить текущую рабочую конфигурацию как baseline_v1, запустить существующий сенсорный стек (OwnedTestWindow DXGI + WAV-loopback WASAPI + TelemetryComputer + LiveEvidenceArchive + Qwen Observer на GPU 1 + PersistentWindowsOcrPipe) в непрерывном 60-минутном прогоне при 60 FPS (216 000 кадров). Никаких новых фич, никакого рефакторинга. Единственный deliverable — runtime/instances/soak_h1_60min.json с чекпойнтами каждые 10 минут. AC/инвариант: AC-01, AC-08 — доказательство постоянного присутствия без утечек и накопления отказов. Почему сработает: Все текущие бенчмарки 30-секундные. Только 60-минутный прогон выявит накопление VRAM после ротаций, деградацию OCR-процесса, рост RSS, зависание очередей, скрытые рестарты. Эксперимент: scripts/soak_h1_60min.py; на каждом чекпойнте брать снимок psutil RSS, nvidia-smi VRAM ГП 0/1, размеры очередей, FPS-дельту, число JTI/MP4 файлов, CRC-целостность последнего сегмента. Отчёт с графиками RSS/VRAM по минутам. Приватность: только OwnedTestWindow, без физического экрана/микрофона. Метрика успеха: 0 crash / 0 OOM; RSS ≤ +200 МБ от baseline; VRAM GPU 1 ≤ +500 МБ без монотонного роста; FPS-дельта p95 ≤ 5%; CRC-целостность 100% после каждой ротации. Отклонение: монотонный рост RSS/VRAM или падение FPS <95% базовой → блокирующий дефект, минимальный фикс в этом же цикле. Риски/стоимость: ~1 ч прогон + ~1 ч подготовка. 2. H2 (P0): Полная drop-accounting бухгалтерия внутри soak — никаких «Zero-Drop» без доказательства Суть: Заменить туманное «Zero-Drop Load Shedding» на математически проверяемую цепочку счётчиков по стадиям: captured_dxgi → telemetry_processed → queue_submitted → encoder_accepted → mp4_written → jti_written, плюс явный pending_qsize. Интегральный инвариант в конце soak: captured == jti_written + dropped_archive + dropped_encoder + pending + retention_deleted с точностью ≤5 кадров на 216 000. AC/инвариант: AC-08 — честный учёт потерь не по названию, а по факту. Почему сработает: Без этого любой «0 dropped» — самообман. Если интегральная бухгалтерия не сходится, значит есть скрытая утечка информации (например, кадр прошёл encoder, но JTI-запись упала из-за CRC-ошибки). Эксперимент: Расширить LiveEvidenceArchive.get_metrics() шестью счётчиками; в soak-раннере каждые 10 минут брать снимок в metrics_timeseries; в конце — assert captured == jti_written + dropped_archive + dropped_encoder + pending с допуском. Метрика успеха: Интегральная бухгалтерия сходится ≤5 кадров. Отклонение: расхождение >5 кадров = скрытая потеря → блокирующий дефект. Риски/стоимость: ~30 минут. Интегрируется в H1, не отдельный эксперимент. 3. H3 (P0): Lifecycle start → pause → resume → source-lost → recover → stop внутри soak с независимым psutil-аудитом Суть: Встроить в soak по таймеру 4 события управления: pause на T+15 (2 мин), resume, source_lost (уничтожить OwnedTestWindow) на T+35, повторный pause/resume на T+50. После каждого pause() независимо проверять через psutil.Process().open_files(): 0 открытых .jti/.mp4, 0 DXGI/WASAPI handles, 0 запросов к модели-серверу (по netstat). После resume — проверить отсутствие разрыва PTS. AC/инвариант: AC-08, AC-09 — реальный контроль владельца + отказоустойчивость к сбоям источника. Почему сработает: psutil.open_files() — внешняя проверка, а не внутренняя декларация. Без неё «pause останавливает захват» — обещание, а не факт. Эксперимент: Таймерные события в soak-раннере; перед каждым — снимок psutil.open_files() + netstat к model-server; перед resume — запись последнего pts_us, после — первый pts_us, расчёт gap_ms. Метрика успеха: 0 открытых .jti/.mp4/DXGI/WASAPI handles в paused-состоянии (проверка ≤100 мс после pause); resume: gap_ms ≤ 5 мс; source_lost → recover ≤10 с, 0 crash. Отклонение: любой открытый handle после pause = нарушение AC-09, немедленный фикс. Риски/стоимость: ~1 ч. Интегрируется в H1. 4. H4 (P1): 5-минутный голосовой стресс внутри soak (T+40..T+45) с barge-in на всех фазах Суть: Встроить в soak 5-минутное окно с активной речью: WAV → GigaAM ASR → SenseNova → OmniVoice, 5 сценариев (вопрос о текущей сцене, ретро-вопрос через inspect_segment, barge-in во время VLM, barge-in во время TTS, молчание). Замер voice_end → first_audio и barge_in → halted на реальной конкурентной нагрузке (архив 60 FPS + OCR + Qwen + SenseNova + OmniVoice). AC/инвариант: AC-03, AC-08 — прямое доказательство, что ретро-инспекция не ломает живой голос в реальной конкурентной среде. Почему сработает: Раньше конкуренция проверялась отдельно для ASR и отдельно для Qwen, никогда совместно со всем голосовым трактом. Единственное честное доказательство — одновременная нагрузка всех компонентов. Эксперимент: scripts/soak_h4_voice_5min.py встроен в H1 как подпрогон на T+40..T+45; логировать voice_end_ms, first_audio_chunk_ms, barge_in_ms в per-turn JSON. Без физического микрофона — фикстуры. Метрика успеха: p95 voice_end → first_audio ≤ 4000 мс; p95 barge_in → halted ≤ 300 мс; FPS-дельта ≤5% в окне. Отклонение: p95 barge_in > 300 мс → блокировать sync inspect_segment в голосовом ходе, задокументировать как задачу следующего цикла (двухфазный async-ответ). Риски/стоимость: ~1 ч. Если GPU 1 не выдерживает — это ценный результат (нарушение AC-03), а не провал. 5. H5 (P1): Retention + Forget по фактически записанному soak-архиву — disk-truth Суть: После 60-минутного soak проверить на реальном архиве: (а) объём на диске соответствует retention (например, retention=5 мин → на диске ровно 5 мин, не 60); (б) forget(t1, t2) каскадно удаляет JTI + MP4 + LanceDB + SensoryHistory; (в) du -sh после forget показывает 0 байт за удалённый интервал с точностью до последнего сегмента; (г) повторный inspect_segment на удалённый интервал возвращает ARCHIVE_GAP_UNAVAILABLE, не OBSERVED_ABSENT и не ложный NOT_FOUND_IN_SAMPLE. AC/инвариант: AC-09 — реальный контроль хранения и забывания на объёме 60 минут, а не на 30-секундных фикстурах. Почему сработает: Ретенция под реальным объёмом — единственное честное доказательство. Мелкие фикстуры не выявят баги кольцевого буфера ротаций. Эксперимент: scripts/benchmark_h5_retention_forget.py: du -sh до forget; forget(T+10, T+20); du -sh после; grep -r "<deleted-interval>" по всем хранилищам → 0 ссылок; inspect_segment на удалённый интервал → ARCHIVE_GAP_UNAVAILABLE. Метрика успеха: Disk-delta совпадает с ожидаемым объёмом ±1 сегмент; 0 уцелевших ссылок в 5 хранилищах; post-forget запрос возвращает ARCHIVE_GAP_UNAVAILABLE. Отклонение: уцелевшие файлы/ссылки после forget = нарушение AC-09, немедленный фикс. Риски/стоимость: ~30 минут. Полностью на soak-архиве, без нового захвата. 6. H6 (P1): Независимый vision holdout на 25 новых сценах вне процедурного генератора (после soak) Суть: Все метрики зрения (24/30, 5/5) получены на одном процедурном realistic_gameplay_60fps.mp4. Нужен blind holdout 25 событий: 10 Win32 UI-скриншотов с ClearType 10–14 pt (тёмная/светлая тема), 8 открытых dataset (игры/IDE/браузер), 7 синтетических стыков с 100-мс событиями между узлами сетки. Прогон с текущими порогами без подстройки. Выполняется после soak, чтобы не отбирать GPU. AC/инвариант: AC-02, AC-07 — доказательство обобщения за пределами процедурного генератора. Почему сработает: Жёсткое правило «никаких подстроек между train и holdout» отсекает переобучение. Если точность падает — это документированный дефект, определяющий следующий цикл, а не провал текущего. Эксперимент: scripts/build_blind_holdout_h6.py (без GT в промпте); scripts/benchmark_h6_holdout.py прогон inspect_segment + TemporalEvidenceVerifier; отчёт runtime/instances/h6_holdout_report.json. Метрика успеха: verification_precision ≥ 90%, verified_recall ≥ 65%, false_confirmation_rate = 0%. Отклонение: precision < 85% или recall < 60% → документированный дефект, определяет следующий цикл (не переделываем сейчас). Риски/стоимость: ~1.5 ч. Только после soak, иначе отбирает GPU у H1. Порядок цикла (реально за одну итерацию): H1 (soak) — основной; в него встроены H2 (drop-accounting) и H3 (lifecycle). На T+40..T+45 встроен H4 (голос). После soak-прогона — H5 (retention/forget) и по готовности H6 (holdout). Критерий завершения цикла: H1 PASS + H2 PASS (сходимость бухгалтерии) + H3 PASS (0 handles после pause) = основная приёмка. H4/H5 — обязательные ворота. H6 — рекомендуемый smoke, не блокер текущего цикла. Протокол реагирования на результаты: если soak выявил блокирующий дефект — минимальный фикс в этом же цикле, focused regression, обновление docs/STATE.md, TODO.md, CHANGELOG.md. Если дефект требует многочасового рефакторинга — фиксируем как задачу следующего цикла, не блокируем завершение soak-приёмки.
