Категории банка индексированы по векторам состояния из affective_engine.py (valence, arousal, social_intent):

1. Суть и архитектурный механизм

Главные враги быстрого Barge-In — это: 1) акустическое эхо (микрофон ловит голос самого компаньона из колонок и прерывает сам себя), и 2) ожидание ответа от тяжелого ASR, чтобы убедиться, что это речь пользователя (занимает > 700 мс).

VAD анализирует микрофонный сигнал после вычитания спектра текущего TTS.

Bonsai LLM пересчитывает огромный KV-кэш с новыми визуальными токенами,

Механизм:

В промпт Bonsai передается последний уже готовый текстовый/эмбеддинг-слепок сцены из RAM-кэша (обновляемый в фоне в периоды молчания каждые 2–3 с).
Изоляция CUDA Streams и квотирование VRAM:
Жесткая фиксация лимитов памяти (KV-cache cap для Bonsai + фиксированный пул весов), чтобы пиковое потребление на GPU 1 никогда не превышало 88% физической VRAM (полное исключение ухода в Shared RAM).
Выделение для OmniVoice TTS отдельного высокоприоритетного потока torch.cuda.Stream(priority=-1), чтобы синтез первой короткой клаузы (3–6 слов) не блокировался фоновыми операциями.

1. Суть и архитектурный механизм

H1a: Диагностическая — сквозной timestamp tracing.
В duplex_cascade.py и на стыках модулей вводятся монотонные таймстампы (time.monotonic_ns()) с тегами этапов:

Тег	Где фиксируется	Что измеряет
T_vad_end	VAD сигнализирует конец речи	Отсчёт от конца речи пользователя
T_asr_partial_last	Последний partial-чанк ASR	Стабильность частичного распознавания
T_asr_final	ASR финализирует	Полное распознавание

H1b: Устранение сериализации «полный ответ → синтез».
Наиболее вероятная причина 11–32 секунд: duplex_cascade.py собирает полный текстовый ответ от Bonsai, передаёт его целиком в OmniVoice, OmniVoice синтезирует полный аудио, и только потом всё воспроизводится. Это классическая сериализация трёх этапов. Рефикс:

text
Bonsai: [токен] [токен] [токен] [ПРЕДЛОЖЕНИЕ] [токен] ...
                          ↓ первое предложение обнаружено
OmniVoice:          [первый PCM-чанк] [второй PCM-чанк] ...
                          ↓ первый PCM-чанк готов
Playback:                   [первый звук] [продолжение] ...

Реализация: в duplex_cascade.py заменить вызов llm.generate_full(prompt) на итератор llm.stream_tokens(prompt). Токен-поток буферизируется в текстовый буфер. При обнаружении sentence boundary (./?/!/\n + пробел или пауза >50мс между токенами) буфер сбрасывается в OmniVoice через tts.synthesize_chunk(text_fragment). OmniVoice работает в streaming-режиме, возвращая PCM-чанки по мере синтеза каждого фрагмента. Воспроизведение стартует по первому PCM-чанку.

Мозг не ждёт завершения мысли, прежде чем начать её артикулировать. Stream-first пайплайн — точная инженерная калька этого механизма. H2: Спекулятивный рефлекторный префейс на предсинтезированном PCM-кэше (быстрая дуга, «миндалевидное тело»)
1. Суть и архитектурный механизм

Рефлекторная дуга JAWL должна работать без GPU 1 вообще — как спинномозговой рефлекс без участия мозга. Предложенная механика:

Шаг А: Предсинтезирование. На этапе инициализации компаньона (startup) OmniVoice генерирует библиотеку из ~200 коротких устных реакций и сохраняет их в PCM (16 кГц, mono, int16). Каждая реакция — 0,3–1,5 секунды. Примеры:

Категория	Сэмплы
Подтверждение	«Ага», «Угу», «Понял», «Да-да», «Хм-хм»
Реакция на интересное	«Ого!», «Класс!», «Вот это да!»
Задумчивость	«Хм…», «Ну…», «Давай подумаю…»
Разочарование/ошибка	«Ой», «Ай-ай», «Ничего, ничего»
Пауза/поддержание присутствия	Лёгкое дыхание (0,5с, почти неслышно)

Суммарный размер кэша: ~200 × 1с × 16000 × 2 байт ≈ 6,4 МБ в RAM. Прогретые и записанные на диск. Никакого GPU.

Шаг Б: Триггер. Когда VAD детектирует T_vad_end (конец речи пользователя), а affective_engine.py на CPU по partial-ASR и тону оценивает эмоциональный контекст, рефлекторный движок (reflex_engine.py, новый модуль, работает только на CPU) выбирает и отдаёт один PCM-файл из кэша в playback-owner. Время от T_vad_end до первого сэмпла: VAD latency (~150мс) + affective_engine inference (~50мс) + кэш-lookup (~1мс) + ALSA/PortAudio write (~5мс) ≈ 200–400мс. Не укладывается ли в <400мс — зависит от конкретного реализованного VAD.

Шаг В: Гашение. Как только первый осмысленный PCM-чанк от stream-first пайплайна (H1) готов к воспроизведению, playback-owner (I-02) плавно затухает префейс (50мс crossfade) и переключается на основной поток. Если префейс ещё не закончился — обрывается мгновенно (epoch bump из H6).

Шаг Г: Контроль искажений памяти (I-01). Префейс никогда не произносит утверждений, обещаний или фактов. Только междометия, кинеметические звуки, реакции. Каталог префейсов жёстко хардкодится в whitelist-списке. Функция reflex_engine.select_preface() возвращает только индексы из этого списка — произвольный текст из affective_engine не попадает в кэш.

Это прямое инженерное воспроизведение рефлекторной дуги. Миндалевидное тело в мозгу реагирует на стимул за 100–200мс — не анализируя, а «среагировав» эмоционально. «Хм» на вопрос, «ого» на удивление, вздох на ожидание — всё это происходит раньше, чем неокортекс сформулирует полный ответ. Пользователь получает социальный сигнал присутствия мгновенно, и ощущение «живого» собеседника формируется в первые 400мс, до того как Bonsai вообще начал думать. Это принципиальное улучшение AC-01.

class ReflexEngine:
    def __init__(self, cache_dir="cache/prefaces"):
        self.cache = load_pcm_cache(cache_dir)  # {id: bytes}
        self.last_trigger_time = 0.0
        self.cooldown_ms = 2000
        self.max_consecutive = 3
        self.consecutive = 0

    def select_preface(self, vad_end: bool, emotion: str, partial_asr: str) -> Optional[bytes]:
        now = time.monotonic()
        if not vad_end: return None
        if now - self.last_trigger_time < self.cooldown_ms: return None
        if self.consecutive >= self.max_consecutive:
            if now - self.last_trigger_time < 5000: return None
            self.consecutive = 0
        # Выбор по эмоции из whitelist — никогда не выдаёт утверждений
        preface_id = EMOTION_TO_PREFACE[emotion]  # 'hmm', 'uga', 'ogo', ...
        self.last_trigger_time = now
        self.consecutive += 1
        return self.cache[preface_id]

H3: Токеновый стриминг Bonsai → гранулярный сброс в OmniVoice по границам предложений с overlap-фреймбей
1. Суть и архитектурный механизм

Дополнение к H1 с фокусом на качество стриминга. Ключевая проблема: если отправить OmniVoice обрывок текста («Давай я расскажу тебе...»), а затем следующий («...про этот аниме-сериал. Он мне очень понравился»), качество синтеза может ухудшиться — интонация не совпадёт, будет слышно «склейку».

Решение: overlap-фреймбей. При каждом сбросе буфера в OmniVoice текущий кусок текста отправляется вместе с перехваченным контекстом последних 5–10 символов из предыдущего чанка:

text
Чанк 1: "Давай я расскажу тебе про этот аниме"
Чанк 2: "аниме-сериал. Он мне очень понравился"
              ↑ 5 символов перехвата для контекста

OmniVoice при синтезе чанка 2 видит слово «аниме» как начало, что даёт корректную интонацию и плавный переход. При этом в вывод отдаётся только новый текст (без перехвата).

Механизм sentence boundary detection в duplex_cascade.py:

Python
SENTENCE_END = re.compile(r'[.!?]\s*|\n')
BUFFER_MAX_CHARS = 180
BUFFER_FLUSH_PAUSE_MS = 50  # если токены приходят редко — сбросить по таймау

class StreamingTextBuffer:
    def __init__(self, tts, overlap_chars=8):
        self.text = ""
        self.tts = tts
        self.overlap_chars = overlap_chars
        self.last_flush = 0

    def push_token(self, token: str) -> Optional[AsyncIterator[bytes]]:
        self.text += token
        m = SENTENCE_END.search(self.text)
        if m or len(self.text) >= BUFFER_MAX_CHARS:
            boundary = m.end() if m else len(self.text)
            flush_text = self.text[:boundary]
            self.text = self.text[boundary - self.overlap_chars:]  # сохраняем overlap
            return self.tts.synthesize_stream(flush_text)
        return None
2. Почему сработает и как соотносится с биологической моделью

Неокортекс не выдаёт моторной коре абстрактные символы. Моторная кора (артикуляция) получает фонетическую программу с контекстом. «Как произнести следующий слог» зависит от того, как заканчивался предыдущий. Overlap-фреймбей — это инженерный эквивалент фонетического контекста. Результат: звучание без «склеек», интонационно цельное, даже при стриминге. Пользователь слышит непрерывный поток речи, а не набор синтезированных фрагментов.

H4: Приоритетный CUDA-стрим-планировщик для GPU 1 с принудительным preempt при запросе TTS-first-chunk
1. Суть и архитектурный механизм

Bonsai (LLM) и OmniVoice (TTS) работают на одном GPU 1. Если обе модели генерируют токены/чанки одновременно, они конкурируют за вычислительные ресурсы. В CUDA это можно контролировать через CUDA streams с приоритетами.

Механизм:

Python
# При инициализации GPU 1
import torch

# Низкий приоритет — Bonsai (может быть preempted)
low_prio_stream = torch.cuda.Stream(priority=-1)   # приоритет от -5 до 0, чем ниже — тем приоритетнее

# Высокий приоритет — OmniVoice (первый чанк)
high_prio_stream = torch.cuda.Stream(priority=0)   # 0 = базовый, -5 = наивысший

Когда TTS первый чанк ждёт вычислений:

Bonsai работает в low_prio_stream.
tts.synthesize_chunk(first_sentence) планируется в high_prio_stream.
CUDA-планировщик автоматически вытесняет kernels из low_prio_stream в пользу high_prio_stream.
Bonsai продолжит генерацию после того, как kernels TTS завершатся.

Но: CUDA streams внутри одного процесса работают асинхронно, и приоритеты действуют только на уровне kernel scheduling внутри GPU. Это не вытеснение процессов, а вытеснение kernel-ов. Для полноценного preempt между моделями нужно:

Альтернатива (более надёжная): Временное разделение (time-slicing) на уровне inference.

Python
class GPU1Scheduler:
    def __init__(self, llm_model, tts_model):
        self.llm = llm_model
        self.tts = tts_model
        self.lock = threading.Lock()
        self.tts_priority_pending = False

    def llm_generate_next_token(self):
        with self.lock:
            # Если TTS требует GPU — ждём, пока он закончит
            while self.tts_priority_pending:
                time.sleep(1)  # 1мс poll
            # Генерация одного токена Bonsai
            token = self.llm.forward_single_step()
            return token

    def tts_synthesize_first_chunk(self, text):
        with self.lock:
            self.tts_priority_pending = True
            pcm = self.tts.synthesize(text)
            self.tts_priority_pending = False
            return pcm

Приоритет: tts_synthesize_first_chunk ставит флаг tts_priority_pending = True. Bonsai генерирует токен за токеном (а не целый ответ сразу), и между токенами проверяет флаг. При установке флага Bonsai отпускает lock (или ждёт), OmniVoice получает GPU 1, синтезирует первый чанк (0,3–0,8с), отпускает GPU. Bonsai продолжает.

Ключевой момент: Bonsai генерирует по одному токену за вызов (или по N токенов с проверкой между батчами), а не вызывает generate(max_length=500). Это и есть preemptible point.

2. Почему сработает и как соотносится с биологической модельей

Это аналог приоритетной обработки сигналов в мозге. Когда моторная кора требует ресурсы для артикуляции (TTS), сенсорная кора на время «прекращает» активную обработку. Неокортекс не «вытесняет» задачу рефлектора — он позволяет рефлектору прервать текущую обработку. Bonsai «замораживается» между токенами на 0,5–0,8с, отдавая GPU 1 TTS, и это почти незаметно для пользователя — потому что пользователь слышит первый звук от TTS, а не от Bonsai.

H5: Barge-in с echo-reference AEC и epoch-based мгновенной отменой генерации (≤300мс)
1. Суть и архитектурный механизм

Три компонента barge-in, работающих одновременно:

A: Echo-reference (loopback) AEC.
Когда JAWL воспроизводит свой голос, сигнал из динамиков микрофон ловит как эхо. Без подавления эха компаньон начнёт «понимать» свою собственную речь как речь пользователя и запустит barge-in на своем же голосе. Решение: echo-reference — копия PCM-потока, уходящего в динамики, передаётся в AEC-алгоритм (WebRTC AEC3 или kaldi-mfcc-based AEC) для подавления. Echo-reference берётся из playback-owner перед записью в ALSA/PortAudio:

Python
class PlaybackArbiter:
    def __init__(self):
        self.echo_ref_buffer = bytearray()  # копия того, что играем

    def play(self, pcm_chunk: bytes, turn_id: int, epoch: int):
        self.echo_ref_buffer.extend(pcm_chunk)  # сохраняем для AEC
        alsa_write(pcm_chunk)

B: Мгновенная отмена через epoch-бамп.

Python
class GenerationCoordinator:
    def __init__(self):
        self.current_epoch = 0
        self.current_turn_id = 0

    def on_user_speech_start(self):
        """Вызывается VAD при обнаружении речи пользователя."""
        self.current_epoch += 1  # прежняя генерация «умирает»
        self.abort_llm_generation()       # немедленно прервать Bonsai
        self.flush_tts_buffers()          # очистить все неотправленные TTS-чанки
        self.playback_owner.cut_output()  # обрыв воспроизведения

Каждый чанк несёт (turn_id, generation_epoch, chunk_index). Playback-owner проверяет:

Python
def should_play(self, chunk):
    return (chunk.turn_id == coordinator.current_turn_id and
            chunk.epoch == coordinator.current_epoch)

Любой чанк со старым epoch молча отбрасывается. Это окончательная защита от «поздних» чанков, которые могли быть в очереди до barge-in.

C: Сброс AEC state. При epoch-бампе AEC-алгоритм сбрасывает внутреннее состояние (filter state), чтобы не «фильтровать» следующий ответ пользователя как эхо.

2. Почему сработает и как соотносится с биологической моделью

Когда человек перебивает собеседника, собеседник немедленно замолкает — не дожидаясь завершения предложения. Эта биологическая реакция занимает ~200–300мс (рефлекс остановки речи). В JAWL это соответствует: VAD обнаружил начало речи пользователя → мгновенный abort всего, что делает компаньон → компаньон слушает. Эхо-reference критичен, потому что без него компаньон «слышит» свой собственный голос и непрерывно барджит себя — катастрофа.
