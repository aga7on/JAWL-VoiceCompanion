 Ответ A 1. H1 (P0): 60-минутный сенсорный soak существующего контура с полной телеметрией — единственный и основной результат цикла Суть: Зафиксировать текущую рабочую конфигурацию как baseline_v1, затем запустить существующий сенсорный стек (DXGI-захват OwnedTestWindow + WASAPI-loopback WAV-фикстуры + TelemetryComputer + LiveEvidenceArchive + Qwen Observer на GPU 1) в непрерывном 60-минутном прогоне на 60 FPS. Никаких новых функций не добавлять. Единственный deliverable — отчёт runtime/instances/soak_h1_60min.json с посуточными чекпойнтами каждые 10 минут. AC/инвариант: AC-01, AC-08 — доказательство постоянного присутствия без утечек и накопления отказов. Почему сработает: Все существующие бенчмарки — короткие (30 сек). Только 60-минутный прогон выявит накопление VRAM после ротаций, деградацию OCR-процесса, рост RSS, зависание очередей архиватора, ошибки восстановления после длительной работы. Эксперимент: scripts/soak_h1_60min.py — оркестратор. OwnedTestWindow рендерит процедурную анимацию с читаемыми событиями раз в 8–15 с. WAV-фикстура в loopback (без физического микрофона). Чекпойнт каждые 10 минут: psutil RSS, nvidia-smi VRAM GPU 0/1, размеры очередей архиватора, FPS дельта, число файлов JTI/MP4, CRC-целостность последнего сегмента, время recovery-операций. Отчёт с графиками RSS/VRAM по минутам. Метрика успеха / критерий отклонения: 0 crash / 0 OOM / 0 незакрытых handle после teardown. RSS ≤ +200 МБ от baseline к 60-й минуте; VRAM GPU 1 ≤ +500 МБ без монотонного роста. FPS-дельта p95 ≤ 5%; dropped_archive_frames ≤ 0.1% (≤216 на 216 000). CRC-целостность 100% после каждой ротации. Отклонение: монотонный рост RSS/VRAM или падение FPS <95% базовой → фиксируем как блокирующий дефект, минимальный фикс в этом же цикле. Риски/стоимость: ~1 час прогона + ~1 час подготовки. Приватность: только тестовый Win32-холст, никакого захвата реального экрана/микрофона владельца. 2. H2 (P0): Сквозной drop-accounting — доказательство captured == encoded + dropped_archive + dropped_encoder + pending на всех стадиях soak Суть: В текущем состоянии система заявляет «Zero-Drop Load Shedding», но фактически это drop-on-overload. Нужна математически проверяемая цепочка по всем стадиям: captured_dxgi → telemetry_processed → queue_submitted → encoder_accepted → mp4_written → jti_written, с явным счётчиком pending в очереди на каждом чекпойнте. Интегральная бухгалтерия: разница captured - jti_written на 60-й минуте должна объясняться dropped_archive + dropped_encoder + pending + retention_deleted. AC/инвариант: AC-08 — честный учёт потерь не как «Zero-Drop», а как измеримое число с известной причиной. Почему сработает: Без счёта по стадиям текущие отчёты («0 dropped») не врут, но скрывают реальность: прогон ранее показывал -25% случайных артефактов ASR-тайминга. Возможно, тот прогон в реальности терял кадры, но это было невидимо. Только полная pipeline-bugetary matrix покажет, где реально теряется информация. Эксперимент: Расширить LiveEvidenceArchive.get_metrics(): словарь с 6 счётчиками + pending_qsize. В soak-раннере на каждом 10-минутном чекпойнте брать снимок, записывать в metrics временной ряд. В конце: assert captured == jti_written + dropped_archive + dropped_encoder + pending с допуском ≤ 5 кадров. Метрика успеха / критерий отклонения: Интегральная бухгалтерия сходится в пределах ≤5 кадров на 216 000. dropped_archive > 0 регистрируется с указанием временного интервала, где случился перегруз. Отклонение: расхождение >5 кадров = скрытая потеря данных → блокирующий дефект, минимальный фикс. Риски/стоимость: ~30 минут работы встроить счётчики в LiveEvidenceArchive. Выполняется параллельно с H1 — не отдельный эксперимент. 3. H3 (P0): Pause / Resume / Source-Lost без утечек — контроль внутри soak Суть: В реальной работе владелец будет ставить на паузу, игра может быть свёрнута, DXGI-источник может пропасть. Проверить на живом soak: (a) pause() в T+15 → psutil.open_files() не содержит .jti/.mp4, DXGI handle закрыт, model-server не получает запросов; (b) resume() → запись восстанавливается без разрыва PTS; (c) в T+35 симулировать source_lost (уничтожить OwnedTestWindow) → безопасное закрытие + автовосстановление ≤10 с; (d) в T+45 повторить pause → resume для повторной проверки. AC/инвариант: AC-08, AC-09 — доказательство контроля владельца и отказоустойчивости к сбоям источника. Почему сработает: Аудит psutil — внешняя, независимая проверка. Без неё любое заявление «pause останавливает захват» остаётся декларацией. Эксперимент: Расширить soak-раннер с 4 событиями управления по таймеру. Перед каждым событием снимать psutil.Process().open_files() и netstat к model-server. Проверять dxgi_handle_closed через явный метод. Метрика успеха / критерий отклонения: 0 открытых .jti/.mp4/db файлов и 0 DXGI/WASAPI handles в paused-состоянии (проверка ≤100 мс после pause). Resume: gap_ms ≤ 5 мс между последним PTS до pause и первым после. Source_lost → recover ≤10 с, 0 crash. Отклонение: любой открытый handle после pause = блокирующее нарушение AC-09, немедленный фикс. Риски/стоимость: ~1 час. Интегрируется в soak-раннер. 4. H4 (P1): Concurrent voice + vision — 5 минут soak с активной речью Суть: Soak сам по себе не проверяет конкуренцию ретроспекции с живым голосом. В течение 5 минут soak (T+40..T+45) запустить параллельную цепочку voice WAV → GigaAM ASR → SenseNova → OmniVoice с 5 сценариями: (a) вопрос о текущей сцене, (b) ретро-вопрос о 30-секундной давности → inspect_segment, (c) barge-in на фазе VLM, (d) barge-in на фазе TTS, (e) молчание. Замеры — те же, что AC-03. AC/инвариант: AC-03, AC-08 — доказательство, что ретро-инспекция не ломает живой голос в реальной конкурентной среде. Почему сработает: Всё компоненты уже работают; нужен только совместный прогон с обязательной проверкой barge-in на всех фазах, что никогда не тестировалось в одном окне. Эксперимент: scripts/soak_h4_voice_5min.py встроен в H1 soak как подпрогон. cancel_token в inspect_segment() (добавить минимально, если ещё нет — 20 строк). Логировать voice_end_ms, first_audio_ms, barge_in_ms. Метрика успеха / критерий отклонения: p95 voice_end → first_audio ≤ 4000 мс. p95 barge_in → halted ≤ 300 мс. FPS-дельта ≤5% на этом окне. Отклонение: p95 barge_in > 300 мс → блокировать sync inspect_segment в голосовом ходе, переход на двухфазный async (документировать как следующий цикл). Риски/стоимость: ~1 час. Если GPU 1 не выдерживает — это ценный результат (нарушение AC-03). 5. H5 (P1): Retention + Forget disk-truth на фактически записанном soak-архиве Суть: После 60-минутного soak проверить: (a) реальный объём на диске соответствует retention (например, если retention=5 мин, то после 60 мин работы на диске ровно 5 мин архива, не больше); (b) forget(t1,t2) каскадно удаляет все JTI + MP4 + LanceDB/JSON ссылки, и du -sh после показывает 0 байт остаточных файлов за интервал; (c) повторный inspect_segment на удалённый интервал возвращает ARCHIVE_GAP_UNAVAILABLE, а не OBSERVED_ABSENT. AC/инвариант: AC-09 — реальный контроль хранения и забывания на данных, накопленных в реальном soak. Почему сработает: Проверка на реальном 60-минутном архиве (а не на подготовленных 30-секундных фикстурах) — единственная, что доказывает retention менеджерирование под реальным объёмом. Эксперимент: После H1 soak запустить scripts/benchmark_h5_retention_forget.py: du -sh archive_dir до forget. forget(T+10min, T+20min) — удалить 10-минутное окно. du -sh archive_dir после — дельта должна совпасть с объёмом за 10 мин с точностью до последнего сегмента. grep -r "<forgotten-interval>" по всем JSON/LanceDB → 0 ссылок. inspect_segment на удалённый интервал → ARCHIVE_GAP_UNAVAILABLE (не OBSERVED_ABSENT). Метрика успеха / критерий отклонения: Disk-delta после forget совпадает с ожидаемым объёмом (±1 сегмент). 0 уцелевших ссылок на удалённый интервал в 5 хранилищах. Post-forget запрос возвращает ARCHIVE_GAP_UNAVAILABLE, не OBSERVED_ABSENT. Отклонение: уцелевшие файлы/ссылки после forget = блокирующее нарушение AC-09. Риски/стоимость: ~30 минут. Полностью на soak-архиве, никакого нового захвата. 6. H6 (P1): Независимый vision holdout — 25 новых сцен вне процедурного генератора Суть: Все предыдущие метрики зрения (24/30, 5/5) получены на одном процедурном realistic_gameplay_60fps.mp4. Нужен blind holdout 25 событий на других сценах: 10 Win32 UI-скриншотов c ClearType 10–14 pt (тёмная/светлая тема), 8 скриншотов из открытых dataset (игры/IDE/браузер), 7 синтетических стыков с 100-мс событиями между узлами сетки. Прогон с текущими порогами без подстройки. Только после H1-H5 (не параллельно) — чтобы не отбирать GPU у soak. AC/инвариант: AC-02, AC-07 — доказательство обобщения за пределами процедурного генератора. Почему сработает: Жёсткое правило «никаких подстроек между train и holdout» отсекает переобучение. Если точность падает — это документированный факт, определяющий следующий этап работы, а не провал проекта. Эксперимент: scripts/build_blind_holdout_h6.py — собирает 25 событий без GT в промпте. scripts/benchmark_h6_holdout.py — прогон inspect_segment + TemporalEvidenceVerifier на 25 событиях. Отчёт runtime/instances/h6_holdout_report.json. Метрика успеха / критерий отклонения: verification_precision ≥ 90%, verified_recall ≥ 65%, false_confirmation_rate = 0%. Никакой подстройки констант после прогона. Отклонение: precision < 85% или recall < 60% → документированный дефект, определяет следующий цикл (не переделываем в этом цикле). Риски/стоимость: ~1.5 часа. Выполняется после soak, чтобы не отбирать GPU. Порядок цикла (реально за одну итерацию): H1 (soak) — основной исполнитель, в него встроены H2 (drop-accounting счётчики) и H3 (pause/resume/source_lost по таймеру). На T+40..T+45 встроен H4 (голос). После soak-прогона выполняются H5 (retention/forget) и, если хватит времени, H6 (holdout). Критерий завершения цикла: H1 PASS + H2 PASS (сходимость бухгалтерии) + H3 PASS (0 handles после pause) = основная приёмка. H4/H5 — обязательные заглушки. H6 — рекомендуемый smoke, не блокер.
